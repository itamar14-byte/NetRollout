# CLAUDE.md

## Overview

Network bulk configuration tool that pushes configuration snippets to multiple network devices simultaneously. Two interfaces:
- **CLI** (`src/cli.py`): headless one-time rollout from a devices CSV + commands file — no database
- **Web app** (`src/webapp/` package): Flask app served via Waitress on port 8080, behind nginx; Postgres + Redis

## Commands

Everything runs **from the repo root**: `src` is a package and all imports are `src.*`.

### Run the web app (dev)
The services run in the **dev stack** (`compose.dev.yaml`: the product's Postgres, Redis, nginx and monitoring, project `netrollout-dev`); the app runs on the host:
```bash
docker compose up -d          # the dev stack (.env lists all four compose files)
python -m src.webapp          # the app, from the repo root (PyCharm or a terminal)
docker compose ps             # health; `docker compose down` stops it (data kept in volumes)
```
Open `https://localhost` (nginx → the host app on 8080; certificate in `certs/`, self-signed for localhost/127.0.0.1); Grafana at `https://localhost/grafana/` (signed-in admins only; the dev app shows the sidebar link because `config/runtime.env` sets `NETROLLOUT_MONITORING=monitoring`). After changing an image's source (`deploy/…`, the Dockerfile): `docker compose up -d --build`. The repo's `.env` (gitignored) holds the stack's generated passwords — a new checkout gets it, `config/runtime.env` and a localhost certificate from `python -m src.setup init --dev` (there is no `.env.example`); `config/runtime.env` points the host app at it (`127.0.0.1`, not `localhost`: the stack publishes IPv4 only and Windows waits ~2 s on every refused `::1` attempt). Every start runs the Alembic migrations, seeds the factory `admin`/`admin` account if missing, and prunes old log files; the nightly clean-up runs in the app (`src/webapp/retention.py`). There is no separate DB-init step.

### Install / manage (Windows): NetRollout Setup + `bin\manage.ps1`
Windows installs only through **NetRollout Setup** (below); the installed folder: `bin\` (NetRollout Manager.exe, manage.ps1, netrollout.bat, netrollout.ico), `deploy\`, the compose files, `VERSION`, `LICENSE`, the uninstaller, and from the install `.env` (hidden), `config\`, `certs\`, `logs\`, `backups\`. In the repo the sources stay in `windows\` (and `linux\`); packaging maps them to `bin`. `bin\netrollout.bat <command>` (start / stop / status / open / logs / help) is the admins' command line; NetRollout Manager is people's. The install folder is the script's parent; the script does what needs the host (checks, Docker — installed through winget / Docker's installer when missing, started and waited for —, busy ports with their owners, `docker compose` with the version from `VERSION`, `icacls`, the desktop + Start Menu shortcuts with `windows\netrollout.ico`) and calls the setup core in the app image (`docker run … python -m src.setup init | prepare-start | status | restore-key | check-update | upgrade | release | port-next | port-open | port-trying | port-close`; `check-update --installed X --new Y` runs with the *installed* image before any file is replaced: `update` / `same` (a repair) / exit 2 for an older one (PEP 440: 1.0.0.dev0 < 1.0.0rc1 < 1.0.0); `upgrade` after an update's files: `.env` gets the keys this version needs (`files.UPGRADE_DEFAULTS` — a secret the data depends on is never made up: missing → refused) and an `# Updated to NetRollout X on …` line). `install` runs only from NetRollout Setup (`-Yes` + the answers; it hides `.env`); `defaults -Out <ini>` gives the wizard its pre-fills, the timezone list and any reason NetRollout can't run here (Windows Server, virtualization off); `-NoBrowser`; `NETROLLOUT_PROJECT` = another compose project name (tests). PowerShell 5.1: native stderr under `Stop` becomes an error (`Invoke-Native`), a function's native output is captured (`-Talk` uses `Start-Process`), a script-block certificate callback can't run (`NrLocalTls`, compiled: self-signed accepted for 127.0.0.1 only). Dot-sourcing it loads the functions only.

**The Windows app** (9.3b): `windows\installer\netrollout.iss` → `dist\NetRollout-Setup-<version>.exe` — the only Windows install (Inno Setup 6; compile: `docker run --rm -v "<repo>:/work" amake/innosetup windows/installer/netrollout.iss`, after `windows\manager\build.ps1`). Before its first page it refuses Windows Server / virtualization off (the script's `defaults`). The wizard: licence (`windows\installer\licence-notice.txt`, then the repo's `LICENSE` below a line, added at run time line by line so it keeps the theme's text colour) → Docker (`manage.ps1 ensure-docker -Yes`) → install location (C:\NetRollout pre-selected) → Settings (an OVF-style form pre-filled by `defaults`: hostname, port with busy ports named, Windows' timezone list, monitoring, certificate files; skipped when the folder already holds a kept install) → the review page (every choice) → `manage.ps1 install -Yes -Hostname … -HttpsPort … -Monitoring … -OrgCertificate … -TimeZone …` (output in `logs\install.log`, its tail shown on failure). **Over an install it updates** (9.6b): `FindInstalled` reads Windows' install record (HKCU Uninstall `{AppId}_is1` → InstallLocation) + that folder's `VERSION`; only the review page ("Ready to update X → Y", button Update; Docker's page if it isn't running); `PrepareToInstall` runs the temporary copy `manage.ps1 prepare-update -InstallDir <install> -NewVersion Y` **before any file is replaced** (`check-update` with the installed image — an older Setup is refused, exit 7 silent, nothing changed; the same version = a repair — then a `before-update` backup by the installed version); after the files `manage.ps1 update -Yes` (compose pull while the old version runs, our two images (app, nginx) checked → exit 3 when not published, `setup upgrade`, restart); log `logs\update.log`. **Test builds**: `iscc /DTestBuild` → `NetRollout-Setup-<v>-test.exe`, "NetRollout (test)" with its own AppId — Windows keeps one install record per AppId and user, so a test install with the real id takes over (and its uninstall deletes) the real one's record; never test with the real build. Per user (no UAC for NetRollout itself), Settings → Apps entry, Start Menu + desktop + "tray at sign-in" (`--tray`) + "add to PATH" (`bin` in the user PATH: `netrollout status` in any terminal — the script is `manage.ps1`, not `netrollout.ps1`, because PowerShell would run a `netrollout.ps1` before the `.bat` and Windows' default policy refuses scripts) + always Win+R `netrollout` (App Paths → the Manager), both removed on uninstall; a failed set-up offers Retry (a fixable cause; once `.env` exists a retry runs `start`) or only OK when the script exits 3 (the release's image is missing: "report it"), then the finished page says "installed, but not running" with the next step (Manager → Start ticked when `.env` exists, else run Setup again; no browser link); success ticks "Open NetRollout in the browser"; message boxes are `SuppressibleMsgBox` (silent runs). the uninstaller runs `manage.ps1 uninstall -Yes -KeepData|-DeleteData` (asks; silent keeps). `windows\manager\NetRolloutManager.cs` → `windows\NetRollout Manager.exe` (installed in `bin\`) (C# 5, .NET Framework 4.8, Windows' own `csc.exe` via `build.ps1`; not committed): status light from `/_netrollout/health` on 127.0.0.1 (self-signed accepted for 127.0.0.1 only), actions run `manage.ps1` hidden, **Update** (9.6c, `windows\manager\Updates.cs`: GitHub's latest release — `HKCU\Software\NetRollout\Manager\UpdateFeed` = a mirror or test feed in the same JSON, file or http links; the update window shows the notes and what happens, **Update now** = Enter: the Setup downloaded to %TEMP%, checked against the release's `SHA256SUMS` (a mismatch is deleted), run `/SILENT` through a hidden `cmd … & start` that reopens the Manager whatever the outcome — it then shows `logs\update.log`'s last line; a daily check, first a minute after start, announces a newer version in the tray once a day (`Announced`), switchable off — `DailyCheck` in the same key, the tray menu, the update window), tray icon (a click opens the window), one instance per install folder (a hash of it in the mutex / event names: a test install's Manager runs next to the real one) (launching it again brings the running one's window forward: a named event; `--tray` adds nothing); `--snapshot <png>` renders the window. `netrollout.ico` holds BMP frames (.NET Framework can't read PNG-compressed ones). The wizard: `WizardStyle=modern dynamic windows11 includetitlebar` (Inno 6.7 draws its own controls — the native check boxes are clipped at 200% DPI; follows Windows' light/dark mode; the small image is a transparent PNG).

### Install / manage (Linux): `linux/netrollout.sh`
`sudo ./linux/install.sh [--yes --hostname … --https-port … --monitoring y/n --org-certificate y/n --timezone …]`, `sudo ./linux/netrollout.sh start | stop | status | open | logs [service] | backup | restore <file> [--no-safety-backup] | uninstall [--delete-data|--keep-data] | help` (no command: the numbered menu, with Back up / Restore). **`update [--version X] [--from <zip>] [--feed <url|file inside the folder>] [--check] [--yes]`** (9.6d; menu 8): `python -m src.setup release` (`src/setup/release.py`, in the installed image) finds the release (GitHub's latest / `tags/vX`, or a feed in the same JSON), downloads `netrollout-<v>-linux.zip` + `SHA256SUMS` (a mismatch deleted; a `--from` zip is checked against a `SHA256SUMS` next to it when there is one) and unpacks it to `.update/netrollout/` → `check-update` with the installed image (older refused, exit 2) → asks (unless `--yes`) → `before-update` backup → `bin/`, the compose files, `deploy/`, `VERSION`, `LICENSE`, `README.md` replaced (rm + copy) → `exec` the **new** script's `update-finish` (pull while the old version runs, our images checked → exit 3, `setup upgrade`, restart, `.update/` removed). The release contract (stage 10 makes it) is in `release.py`'s docstring. Backup and restore follow the Windows script step for step; `restore-key` needs no `--user 0` here (the setup core always runs as root on Linux); Grafana's password is piped by `printf` (bash adds nothing). Bash, the whole body in `main` (read before it runs, so `update` can replace the file). As root: Docker, `.env` (root 600); `config/`, `certs/`, `logs/` and `backups/` (700: the scheduled backups hold the encryption key) owned by the app container's uid 10001 — set at every start, so an older install heals. Docker Engine + the compose plugin are checked and explained, never installed. Busy ports from `ss` (docker-proxy → another container), IPs from `ip` (Docker's bridges left out), the timezone from `timedatectl` / `/etc/localtime`. The same setup-core calls as Windows (`init`, `prepare-start`, `status`). **Both scripts run compose from the install folder**: compose reads `.env`'s `COMPOSE_FILE` relative to the folder it runs in, not to `--project-directory`. Verified in an Ubuntu 24.04 container with its own Docker Engine (Docker-in-Docker); ShellCheck clean.

### Run the CLI
```bash
python -m src.cli -d <devices.csv> -c <commands.txt> [-vf] [-v]
```
- `-vf` / `--verify`: after the push, read each device's config and check every command; `-v` / `--verbose`: print logs to the console (always written to `logs/`)
- Missing paths are prompted for (asked again until the file exists); a prompted run also asks verify and confirms ("About to push N commands to M devices") before the push — full-flag runs never ask. The verify choice is always printed. Exit code: 0 all devices succeeded, 1 mixed, 2 nothing applied (including a stop before the push: missing file, no devices or commands left), 130 Ctrl+C. Every exit but Ctrl+C waits for Enter when run from a terminal, so a double-clicked window stays readable. `--version` prints the version.
- **Standalone `netrollout-cli.exe`** (no Python needed; same flags): `pyinstaller --clean --noconfirm netrollout-cli.spec` from the repo root in the dev venv → `dist/netrollout-cli.exe` (one file, ~15 MB, ~2 s startup; logs go to `logs/` next to it). The CLI must not import the web stack — `tests/unit/test_cli.py` guards it, and the spec excludes it. The exe is unsigned: Windows Defender / SmartScreen may flag it (code-signing is post-v1.0).

### Build the app image
```bash
docker build -t netrollout .                              # the version is the VERSION file
docker build --build-arg VERSION=1.0.0 -t netrollout .    # a release: the label; fails unless it equals VERSION
```
`python:3.12-slim-bookworm`, non-root `netrollout` (uid 10001), `NETROLLOUT_DEPLOYMENT=docker`, `NETROLLOUT_HOME=/data`; health check on `/_netrollout/health`. Context = the `.dockerignore` whitelist (also `VERSION` and Grafana's setup + dashboards, run by the `grafana-setup` service from this image — no bind mounts). The footer (`templates/_footer.html`) shows the version and links the source of that version (AGPL §13).
- Postgres: the **official `postgres:17-bookworm`** image, no extension (9.9a: pg_cron and the custom image dropped — the clean-up runs in the app; bookworm kept, as another base could change collations under an existing database), `timezone`/`log_timezone` from `TZ` (compose `command`). First start only (empty volume): `deploy/initdb/10-netrollout.sh`, mounted from the install folder into `/docker-entrypoint-initdb.d`, creates the logins `netrollout` (the app: owns the `netrollout` DB and `public`, not a superuser) and `grafana_reader`; env `POSTGRES_PASSWORD`, `NETROLLOUT_DB_PASSWORD`, `GRAFANA_DB_PASSWORD`. Installs from before 9.9a keep a pg_cron extension and jobs in their database: inert (no library loaded), never touched. NetRollout needs any PostgreSQL 13+ (`gen_random_uuid()`), no extension, no special server setting. At every start `install()` gives `grafana_reader` SELECT on exactly `GRAFANA_TABLES` (`device_results`, `job_metadata`, `audit_log`) when the role exists.
- nginx image (`deploy/nginx/`, `docker build -t netrollout-nginx deploy/nginx`): `nginx:1.30-alpine`; one site template (`site.conf.template`) rendered from values — env `NETROLLOUT_HOSTNAME`, `NETROLLOUT_HTTPS_PORT`, `APP_UPSTREAM`, overridden by `shared/site.env` (the app, stage 8; values are validated, never nginx syntax). Other names redirect to the hostname (IPs and localhost are served); port 80 → `https://<host>:<port>`; `/rollout/stream/` unbuffered; `/metrics` 404; the app looked up per request (Docker DNS, 10 s). `netrollout-watcher.sh`: waits for the certificate at boot; every 3 s (`NETROLLOUT_WATCH_INTERVAL`) a change of `site.env` or the certificate is rendered + `nginx -t`-tested in staging, then swapped in and reloaded, else the last good site keeps serving; the outcome in `shared/status.json` (`applied`/`rejected` + nginx's message).
- **Grafana** (monitoring profile): served by nginx at `/grafana/` to **signed-in NetRollout admins only** — nginx's `auth_request` asks the app (`/_netrollout/grafana-auth`: 204 + `X-NetRollout-User`, 401 → sign-in, 403 → "admins only"), Grafana runs in proxy-auth mode trusting `X-WEBAUTH-USER` (always set by nginx from that answer; a browser's own is replaced, `Authorization` dropped); every Grafana user is an Editor, no login form. Admins only because free Grafana lets anyone signed in query every datasource through its API (operators: post-v1, a separate organization — workplan). `grafana-setup` (app image, `deploy/grafana/setup.py`) keeps the layout: `NetRollout` → `Operations`/`Jobs`/`Security` (the shipped dashboards, dashboard v2 files in `deploy/grafana/dashboards/<subfolder>/`, re-imported, **view-only**) and `Custom` (the admins': create/edit/nest; never touched — backups must include Grafana's volume). It re-applies every 5 min and stays running (`up --wait` counts an exited container as a failure). **The NetRollout database data source** (uid `cfjxoedixn7r4d`, which the dashboards use; name "NetRollout database") is kept by grafana-setup through Grafana's API, not provisioned (a provisioned one is read-only): from `config/runtime.env` (mounted read-only; `PG_*` / `DATABASE_URL`, a host's 127.0.0.1 = the bundled `postgres`, `NETROLLOUT_GRAFANA_SSLMODE` written by the move from the app's own `pg_stat_ssl`), else the bundled database; the file is looked at every 5 s, a change applied at once (a database move: verified, 5 s); login `grafana_reader` with `GRAFANA_DB_PASSWORD` (grafana-setup's env, no longer Grafana's). The provisioning file deletes the earlier versions' provisioned `postgresql` by name (`deleteDatasources`); until Grafana restarts after an update, grafana-setup reports "restart Grafana" instead of failing silently. In a schema of its own, `grafana_reader` gets `search_path` = that schema per database (the DBA's SQL / the administrator-login way). The admin sidebar's Grafana glyph shows when `NETROLLOUT_MONITORING` contains `monitoring` (compose passes `COMPOSE_PROFILES`).
- The app → nginx (`src/webapp/proxy_config.py`): `write_site()` writes `site.env` in `config/nginx/` (shared with nginx) — the System Settings hostname plus the **applied** HTTPS port (`NETROLLOUT_HTTPS_PORT` from compose, not the setting, which waits for `netrollout apply`) — atomically and only when it changes; `read_status()` / `wait_for_status()` read the watcher's verdict (`None` = no nginx reports there). Every app start syncs it (`sync_at_start`, never blocks the start); the dev stack's nginx shares the repo's `config/nginx`, so dev follows too. **Saving the hostname** (System Settings, `admin_settings._save`) is all or nothing: `settings.plan()` validates without writing; `proxy_config.change_hostname()` reissues a self-signed certificate for the new name (keeping its IPs, and the previous names for a 7-day transition — deadlines in `certs/.old-names.json`, dropped by `drop_expired_names()` at start and hourly, `start_certificate_upkeep`; an organisation's certificate is never reissued) or refuses when the organisation's doesn't cover it, then writes `site.env` (any failure → `ProxyError`, files restored); the setting is saved; nginx's verdict for that hostname is awaited — rejected → setting, `site.env` and certificate put back. The page shows applied / not managed (own proxy) / no answer, or the reason under the field. The Access card always shows `proxy_config.overview()` — nginx's last verdict (applied / rejected + nginx's message, when) and the certificate in use checked by `certs.validate` against the saved hostname (names, expiry, self-signed or not, problems/warnings, old names in transition); it comes with the page, every save, and (in Docker) the Test button, which can't probe the published port from inside. **Server Management → TLS Certificate** (`admin_servers`, the same status via `templates/_access_status.html`): upload an organisation's certificate + key (`proxy_config.install_certificate`: `certs.validate` against the saved hostname first — any problem refuses it; key written first; the self-signed marker and old names removed) or **Generate self-signed** (`generate_selfsigned`: the saved hostname, else the current certificate's name, keeping its IPs); both wait for nginx's verdict (`proxy_config.verdict`) and put the previous files back on a rejection; audited (`server.certificate_uploaded` / `_generated`, never the key).
- **`config/nginx/site.env`** (`src/site_env.py`, the only code writing it; keys updated together under a lock, the file replaced atomically): the hostname and the port in use (nginx reads only these two), the port request, its id and time, and its confirmation (the port helper's); the installer writes the first hostname there and the app seeds System Settings from it at the first start (`proxy_config.seed_hostname_from_site`). Compose passes nginx no hostname or port and the app no seeds; the app gets the published port and `NETROLLOUT_SERVER_IPS` (in every generated self-signed certificate).
- The HTTPS port → the **port helper** (app side `src/webapp/port_apply.py`; decisions `src/setup/port.py`; Docker by the scripts' `apply`; contract in `docs/plans/stage-9.md`): the setting is the **desired** port; saving (or Reset) writes the request into `site.env` (port + a new request id) before the setting, all or nothing. The helper opens the new port next to the old one — a trial file `config/port-trial.yaml` (`P:443` for nginx) listed in `.env`'s `COMPOSE_FILE` for the trial, nginx recreated (`up -d --no-deps --wait nginx`; nginx's config never changes for a port: it always listens on 443 inside) → `apply-status.json`: `trying`; the page served on the new port confirms (`/admin/settings/port/confirm` → `site.env`'s `PORT_CONFIRMED`; checked against the Host header's port and the deadline) → kept (`.env` `HTTPS_PORT`, `site.env`'s port in use, the trial removed); not confirmed within 120 s → rolled back. The 120 s are timed by the script's stopwatch (Docker Desktop's VM clock lagged Windows' by minutes once); a second `apply` waits for the lock, the running one looks again after a keep. **Automatic**: Windows — `NetRollout Manager.exe --helper` (headless, own single-instance lock; Startup entry, Setup's end, `netrollout start`; watches `site.env`, starts `apply` when a request is pending; `logs\port-helper.log`); Linux — systemd `netrollout-port-<project>.path` (`PathModified=` site.env) → `.service` (`apply --yes`), written at every start, removed by uninstall; no systemd → by hand. Where a helper runs, `port-ready` writes a first status so the page waits for it instead of saying "run netrollout apply". Everything that shows or redirects to an address uses `serving_port()` (the helper's status, else `NETROLLOUT_HTTPS_PORT`). Page states: manual (no helper: `netrollout apply`) / waiting (bounded, `WAIT_SECONDS`) / trying / confirming / rolled back + Try again; its polls are background requests.
- TLS certificates (`src/certs.py`, inside the image so the host needs no OpenSSL): `python -m src.certs selfsigned --host <name> [--ip <addr>]...` writes `fullchain.pem` + `privkey.pem` + a `.selfsigned` marker (ECDSA P-256, 825 days, the IPs as SANs) to the certs folder; `validate --cert --key [--host]` checks key match, encrypted key, dates, SAN/wildcard coverage, chain order.

### Run tests
```bash
pytest                    # all
pytest tests/unit         # hermetic, no services
```
Integration tests use a real Postgres (`rollout_test` DB, created on the dev stack's Postgres as its superuser — password from `.env`; `TEST_PG_ADMIN_URL` overrides) and Redis (db 15, the server in `config/runtime.env`) and are skipped with a reason when a service is unhealthy — if ~150 skip right after `docker` starts, Postgres wasn't ready; rerun. ### Migrations
```bash
cd src/db && alembic revision --autogenerate -m "..."   # new migration
```
The app applies migrations itself at startup; the alembic CLI resolves `DATABASE_URL`, else `PG_*`. History starts at the `v1_0_0_baseline` revision (the development migrations were squashed); from v1.0.0 on, released migrations are never edited or squashed — every schema change is a new revision.

### Configuration
- Folders (`src/runtime.py`, resolved per call): `NETROLLOUT_HOME` (image: `/data`), else the exe's folder when frozen, else the repo root → `logs/`, `config/`, `certs/`.
- Connection settings: `DATABASE_URL` or `PG_HOST/PG_PORT/PG_NAME/PG_USER/PG_PASSWORD/PG_SCHEMA`; `REDIS_URL` or `REDIS_HOST/REDIS_PORT/REDIS_DB/REDIS_PASSWORD`. Precedence: `config/runtime.env` (app-owned, written only by a Server Management switch, loaded with override) > the environment (in Docker: the installer's compose `.env`) > defaults. A switch writes every key of that service, blank when unused (URL, password, schema), so nothing inherited can override it. Dev keeps its settings in `config/runtime.env`.
- Other env: `SECRET_KEY`, `PORT` (internal app port, set at install), `NETROLLOUT_THREADS` (Waitress worker threads, default 32, 4–256: an open live rollout log holds one for the whole rollout, and with as many open logs as threads every other request waits — measured 7 s with Waitress's default of 4).
- **System Settings** (admin panel → System; `src/db/settings.py`): retention periods, concurrent rollout jobs, devices per job, reachability cache, canonical hostname + HTTPS port. The `system_settings` table is the only runtime source: `install()` seeds every missing setting at each start (from `ORCHESTRATOR_WORKERS`, `NETROLLOUT_PUBLIC_HOSTNAME`, `NETROLLOUT_HTTPS_PORT` if set, else the default) and never overwrites; after that env vars are ignored. Cross-setting rules are declarative and enforced on the server and in the page.
- Deployment (`src/runtime.py`): `NETROLLOUT_DEPLOYMENT=docker` (set by the image) → `SECRET_KEY` and the encryption key are required (never defaulted or generated), Restart exits and the restart policy brings it back, no startup proxy probe (one log line with the expected URL instead). Dev: a missing `SECRET_KEY` gets a random per-run key.
- Startup in dev (`src/webapp/startup.py`): verifies nginx forwards to this instance (per-run token at `/_netrollout/instance`) and prints the address to use — the System Settings hostname + serving port, else `https://localhost`; opens it in the browser on desktop launches (`NETROLLOUT_OPEN_BROWSER=0` to disable).
- Stop / Restart drain (`src/webapp/lifecycle.py`, `RolloutOrchestrator.drain`): on SIGTERM or the admin Restart, new rollouts are refused (banner on every page), queued ones are recorded as cancelled, running ones finish within `NETROLLOUT_DRAIN_SECONDS` (default 600) and are cancelled after. Restart with rollouts running asks: when finished / now.
- **Maintenance mode** (`src/webapp/maintenance.py`, `app.maintenance`; for the database move, 9.8): **waiting** — `orchestrator.pause()`: new rollouts refused (`Paused`, a `Draining` whose text is the message), queued and running ones finish, nothing cancelled, `resume()` never undoes a drain; banner `_maintenance_banner.html` — then **locked** once `orchestrator.idle()` (no job queued, running or still writing its results): the first request hook answers every request 503 + `Retry-After` (`maintenance.html` for pages, JSON otherwise), the moving admin's included, except views marked `@during_maintenance` (health, instance, Grafana's auth check — they don't write) and `static` / `prometheus_metrics`; `web.audit` prints instead of writing; the scheduled backup and the retention fallback wait (`hold`). In memory only: a restart ends it (the move's switch is its last step). `tests/integration/test_maintenance.py` sweeps the whole url_map.
- Health: `/_netrollout/health` (public) — Postgres/Redis up, running/queued rollouts, draining, maintenance (`null` or state + progress; still 200), version; 200 or 503. Version: the `VERSION` file (`runtime.VERSION`; copied into the image, bundled into the `.exe`).
- Session lifetime (`src/webapp/extensions.py`, `enforce_session_lifetime`): a session ends after `session_idle_minutes` (System Settings → Sessions; default 15, 5–480) without user activity and after 12 hours however active (`ABSOLUTE_SESSION_HOURS`); then a page gets the sign-in with `?next=`, an XHR 401 JSON, Grafana's auth check a bare 401; audit `auth.session_expired`. Activity = what a person does; background requests (header `X-NR-Background: 1`, `?_bg=1` on Active Jobs' auto-reload, the live log stream) are checked for expiry but don't extend. `templates/_idle_timeout.html` (in all three skeletons) warns a minute ahead ("Stay signed in"), asks `/account/session` before leaving (another active tab keeps it) and every 30 s in the background, so a session ended elsewhere (Terminate Session, a reset) leaves the page within 30 s. **Every app start signs everyone out** (`setup.clear_sessions`) — deliberately: a restart, update or reboot starts clean; the Restart button says so and asks.
- Passwords (`src/passwords.py`, local accounts): one rule — 8+ characters, at least 2 of letters / digits / special, ASCII, not containing the username — for registration, `/account/password` and admin resets (a temporary password shown once). `users.must_change_password` (the seeded `admin`, after a reset) gates every page to the change page; that forced change doesn't ask for the current password (the sign-in just proved it) but still refuses it as the new one — only a voluntary change asks for it. On every password field, a rule problem shows once the field is left; only what more typing can't fix (non-ASCII, the username) shows at once (`_password_rule_script.html`). A reset or Terminate Session signs the user out everywhere, a change signs out the user's other sessions (`utils.end_user_sessions`).
- Encryption key: `NETROLLOUT_ENCRYPTION_KEY`, else (dev only) `~/.netrollout/encryption.key`. The app refuses to start on a malformed, missing-with-data, or mismatched key (fail-fast).
- Dev DB: the dev stack's `netrollout` database, owned by the `netrollout` role (not a superuser) — `docker compose exec postgres psql -U postgres -d netrollout`. Moved from the hand-made `NetRollout-DB` container on 2026-10-04 (backup in `backups/`).

### Backups (`src/backup.py`, stage 9.5)
`python -m src.backup create [--kind manual|scheduled|before-restore|before-update] | check <zip> | restore <zip> [--grafana-dir] [--https-port] [--key-out]` → `backups/netrollout-<version>-<YYYYMMDD-HHMMSS>-<kind>.zip`: `manifest.json` (version, migration level, row counts), `db/<table>.csv` (NetRollout's tables, one read-only REPEATABLE READ snapshot, `COPY … CSV HEADER`), `grafana.db` (SQLite online backup of the read-only mounted volume), `certs/`, the rollout logs, `encryption.key` — the zip is as secret as `.env` (owner-only). Through the **app's own connection** (runtime.env over the environment), never a superuser, so it works on the bundled database or an organisation's. **Restore** (NetRollout stopped; one transaction): `alembic downgrade base` (NetRollout's own tables only — anything else in that schema survives) → `upgrade <backup's level>` → `COPY` in FK order → sequences → the key must decrypt a stored credential → `https_port` := this install's → audit `backup.restored`; any failure rolls back. Then certs (with their markers; a backup without one keeps this install's), logs, Grafana; files take the folder's owner when run as root. Refuses a newer version / unknown level / incomplete zip; the app migrates an older one forward at its start. Kept from this machine: `.env` but the key, config/. `prune(keep)` deletes only the oldest *scheduled* backups; one backup or restore at a time (`.backup.lock`, stale after 2 h).
**In the app** (9.5b): System Settings → **Backups** card — `backup_schedule` off/daily/weekly (default daily), `backup_time` (02:00, server-local), `backup_weekday`, `backup_keep` (14) — a `Setting` with `choices` renders as a dropdown. `src/webapp/backup_schedule.py` (thread from `__main__`, first check after 2 min, then every 30 s): due when a scheduled time passed since the newest *scheduled* backup in the folder (a missed one is caught up once); then `prune`; outcome in `backups/.schedule-status.json`; a failure → audit `backup.failed` (actor `scheduler`), an ACTION NEEDED line, retried after an hour. `/admin/backups` (`admin_backups.py`, admins): list, POST = Back up now, `/<name>` download, `/<name>/delete` — names must match `NAME_RE` inside the folder; all audited (`backup.created/downloaded/deleted/failed`). Restore isn't in the UI (it stops the app): **`netrollout backup` / `restore <file> [-NoSafetyBackup]`** (Windows `manage.ps1`; NetRollout Manager's **Back up** / **Restore…** — a file picker in `backups\`, confirmed). Backup: `compose exec app python -m src.backup create` (app stopped: `up postgres` + `compose run --no-deps app`). Restore: copy into `backups\` if elsewhere → `check` → ask (unless `-Yes`) → a `before-restore` backup → stop app (+ grafana-setup, grafana) → `compose run --no-deps --user 0 [-v <project>_grafana:/data/grafana-restore] app python -m src.backup restore <name> --https-port <HTTPS_PORT> --key-out /data/backups/.restored-key [--grafana-dir …]` (fails → started again as it was) → `python -m src.setup restore-key` **as root** (the key file is root's 600; it writes `NETROLLOUT_ENCRYPTION_KEY` into `.env`, removes the file) → Grafana started alone (`up --wait grafana`, not grafana-setup) → its admin password reset to `.env`'s (`grafana cli … reset-admin-password --password-from-stdin`, fed by `printf` from an env var passed through — never piped from PowerShell 5.1, which adds a BOM and CR LF) → start (grafana-setup signs in with the right password from its first run). **Release gate verified** (9.5e): a backup of install A restored onto a fresh install B — B takes A's key, keeps its own passwords, decrypts A's credentials, has A's dashboard, Grafana accepts B's admin password, no grafana-setup failure. `netrollout status` shows a Backups line (count, size, newest, a failed scheduled one → What to do). Compose gives the app `./backups:/data/backups`, `grafana:/data/grafana:ro` and `group_add: ["0"]` (Grafana's `grafana.db` is 640 472:0).

## Architecture

Full architecture in `docs/architecture.md`; plan and current status in `docs/workplan.md` (status table under "Remaining work"). Phase 4 (packaging v1.0.0) is planned in `docs/plans/phase-4.md`.

Retention (defaults; System Settings): job record (results + metadata) 30 days, config snapshots 7 days, audit log 90 days — the **nightly clean-up runs in the app** (`src/webapp/retention.py`: daily at 03:00 server time on whatever database it's connected to, a missed time caught up once, a failure retried after an hour; `db_install.run_retention` runs `RETENTION_STATEMENTS`, which read the setting's row at run time; the last outcome in `config/retention-status.json`, shown on System Settings → Retention); log files 60 days (app-side, daily).

### Rollout job state
`src/job_store.py` (`JobStore`) owns the Redis job keys (`job:{id}:meta`, `user_jobs:{uid}`, the queue, the pending/active counters): the orchestrator writes through it, the pages and the Prometheus collector read through it — no other code spells a key. Every start clears leftover job state (`setup.clear_stale_jobs`: jobs live only in their process, so anything there came from a crash). A finished job (`RolloutOrchestrator._finalize`): results to Postgres (retried; still failing → `logs/unsaved-results-<job>.json` + an ACTION NEEDED console line), then the Redis cleanup and the live log's end — each step runs even if another failed.

### Webapp real-time logging
Server-Sent Events at `/rollout/stream/<job_id>`: history from Redis, then live messages via Redis pub/sub (`job:{id}:logs`), a heartbeat every 0.5s. `X-Accel-Buffering: no` disables nginx buffering.

### Supported platforms (Netmiko device types)
The list is `SUPPORTED_PLATFORMS` (`src/validation.py`, derived from `PLATFORMS`; the pure input checks are module functions there, `Validator` only checks the CLI/import files); how each one finishes a push (save / commit / a command / nothing) and prints its config is the `PLATFORMS` dict in `src/platforms.py` (platform knowledge only, no I/O: also `rejection()` and `verify_commands()`; the SSH is the engine's, `src/core.py`, whose status rules are `classify()`) — adding a vendor is one row there plus a fixture in `tests/unit/test_platforms.py`. Cases only a person can resolve are logged as `ACTION NEEDED — <ip:port>: …` and counted in the rollout summary. Verify (`verify_commands`) places each typed command in its config section and checks presence / absence (`no`/`undo`/`delete`/`unset`); all 12 platforms are covered.

### Device CSV format (shared by CLI and web import)
Required: `ip`, `device_type`, `port`. Optional: `label`; credentials `username`, `password`, `secret`; attribute columns named after a property (by name or label).
- **CLI**: credentials required; attribute columns unused; unreachable devices are dropped before the push.
- **Web import**: attribute columns saved as `var_maps`; credentials become security profiles (checkbox, default on — exact match reuses a profile, otherwise a new uniquely labelled one); unknown columns reported; no reachability check.

## Working style
- The developer writes the code; Claude reviews, advises, and discusses design
- Exception, granted per feature: the developer may approve Claude writing backend code for a specific feature — plan first, stick to the approved plan, and verify on a scratch DB (never the live one) before touching real data
- Always read actual source before suggesting changes
- Frame architecture feedback in terms of encapsulation, minimal API, abstraction, information hiding
- Developer has real networking domain knowledge (3+ years, Netmiko/NAPALM fluency) — no need to explain networking basics
- Distinguish critical issues from design improvements from minor polish when reviewing
- For frontend work, Claude writes the templates/HTML directly (exception to the "developer writes" rule)
- **Changing an existing test needs a proper reason, stated in the commit** — a behavior change the developer approved, a wrong fixture/expectation proven against the source or the vendor's documentation, or a rename. A failing test is a finding first: fix the code, or report it. Never edit an expectation to match what the code now does (retrofitting) without the developer's approval, never loosen an assertion (exact → "somewhere", value → truthy) to make it pass, and never add `skip`/`xfail` to get green. A new test must fail without the change it covers.
