# CLAUDE.md

## Overview

Network bulk configuration tool that pushes configuration snippets to multiple network devices simultaneously. Two interfaces:
- **CLI** (`src/cli.py`): headless one-time rollout from a devices CSV + commands file — no database
- **Web app** (`src/webapp/` package): Flask app served via Waitress on port 8080, behind nginx; Postgres + Redis

## Commands

Everything runs **from the repo root**: `src` is a package and all imports are `src.*`.

### Run the web app (dev)
The services run in the **dev stack** (`compose.dev.yaml`: the product's Postgres, Redis, nginx and monitoring, project `netrollout-dev`); the app runs on the host:
```bash
docker compose up -d          # the dev stack (.env lists all four compose files)
python -m src.webapp          # the app, from the repo root (PyCharm or a terminal)
docker compose ps             # health; `docker compose down` stops it (data kept in volumes)
```
Open `https://localhost` (nginx → the host app on 8080; certificate in `certs/`, self-signed for localhost/127.0.0.1); Grafana at `https://localhost/grafana/` (signed-in admins only; the dev app shows the sidebar link because `config/runtime.env` sets `NETROLLOUT_MONITORING=monitoring`). After changing an image's source (`deploy/…`, the Dockerfile): `docker compose up -d --build`. The repo's `.env` (gitignored) holds the stack's generated passwords — a new checkout gets it, `config/runtime.env` and a localhost certificate from `python -m src.setup init --dev` (there is no `.env.example`); `config/runtime.env` points the host app at it (`127.0.0.1`, not `localhost`: the stack publishes IPv4 only and Windows waits ~2 s on every refused `::1` attempt). Every start runs the Alembic migrations, seeds the factory `admin`/`admin` account if missing, and prunes old log files; the nightly clean-up runs in the app (`src/db/retention.py`). There is no separate DB-init step.

### Install / manage (Windows): NetRollout Setup + `bin\manage.ps1`
Windows installs only through **NetRollout Setup** (below); the installed folder: `bin\` (NetRollout Manager.exe, manage.ps1, netrollout.bat, netrollout.ico), `deploy\`, the compose files, `VERSION`, `LICENSE`, the uninstaller, and from the install `.env` (hidden), `config\`, `certs\`, `logs\`, `backups\`. In the repo the sources are in `packaging\windows\` (and `packaging\linux\`); the release build maps them to `bin`. `bin\netrollout.bat <command>` (start / stop / status / open / logs / help) is the admins' command line; NetRollout Manager is people's. The install folder is the script's parent; the script does what needs the host (checks, Docker — installed through winget / Docker's installer when missing, started and waited for —, busy ports with their owners, `docker compose` with the version from `VERSION`, `icacls` (the whole install folder: Administrators, SYSTEM and the installing account only — at install and every start), the desktop + Start Menu shortcuts with `windows\netrollout.ico`) and calls the setup core in the app image (`docker run … python -m src.setup init | prepare-start | status | restore-key | check-update | upgrade | release | port-next | port-open | port-trying | port-close`; `check-update --installed X --new Y` runs with the *installed* image before any file is replaced: `update`, else exit 2 for the same version (nothing to update) or an older one (downgrades aren't supported) (PEP 440: 1.0.0.dev0 < 1.0.0rc1 < 1.0.0); `upgrade` after an update's files: `.env` gets the keys this version needs (`files.UPGRADE_DEFAULTS` — a secret the data depends on is never made up: missing → refused) and an `# Updated to NetRollout X on …` line). `install` runs only from NetRollout Setup (`-Yes` + the answers; it hides `.env`); `defaults -Out <ini>` gives the wizard its pre-fills, the timezone list and any reason NetRollout can't run here (Windows Server, virtualization off); `-NoBrowser`. PowerShell 5.1: native stderr under `Stop` becomes an error (`Invoke-Native`), a function's native output is captured (so `Invoke-Native` returns it), a script-block certificate callback can't run (`NrLocalTls`, compiled: self-signed accepted for 127.0.0.1 only). Dot-sourcing it loads the functions only.

### Install / manage (Linux): `packaging/linux/netrollout.sh` (installed as `bin/netrollout.sh`)
`sudo ./bin/install.sh [--yes --hostname … --https-port … --monitoring y/n --org-certificate y/n --timezone …]`, `sudo ./bin/netrollout.sh start | stop | status | open | logs [service] | backup | restore <file> [--no-safety-backup] | uninstall [--delete-data|--keep-data] | help` (no command: the numbered menu, with Back up / Restore). `install` checks both images (exit 3 when not published); over a kept `.env` its version stamp decides, as on Windows: same -> start, newer -> refused (exit 2), older -> `check-update` by its image, a `before-update` backup by it (its image gone: refused), then `update-finish`'s steps; no stamp -> older, backed up by this version. `apply` stops with the state it leaves when a `port-*` step fails (Windows' too). **`update [--version X] [--from <zip>] [--feed <url|file inside the folder>] [--check] [--yes]`** (9.6d; menu 8): `python -m src.setup release` (`src/setup/update.py`, in the installed image) finds the release (GitHub's latest / `tags/vX`, or a feed in the same JSON), downloads `netrollout-<v>-linux.zip` + `SHA256SUMS` (a mismatch deleted; a `--from` zip is checked against a `SHA256SUMS` next to it when there is one) and unpacks it to `.update/netrollout/` → `check-update` with the installed image (older refused, exit 2) → asks (unless `--yes`) → `before-update` backup → `bin/`, the compose files, `deploy/`, `VERSION`, `LICENSE`, `README.md` replaced (rm + copy) → `exec` the **new** script's `update-finish` (pull while the old version runs, our images checked → exit 3, `setup upgrade`, restart, `.update/` removed). The release contract (stage 10 makes it) is in `release.py`'s docstring. Backup and restore follow the Windows script step for step; `restore-key` needs no `--user 0` here (the setup core always runs as root on Linux); Grafana's password is piped by `printf` (bash adds nothing). Bash, the whole body in `main` (read before it runs, so `update` can replace the file). As root: Docker, `.env` (root 600); `config/`, `certs/`, `logs/` and `backups/` (700: the scheduled backups hold the encryption key) owned by the app container's uid 10001 — set at every start, so an older install heals. Docker Engine + the compose plugin are checked and explained, never installed. Busy ports from `ss` (docker-proxy → another container), IPs from `ip` (Docker's bridges left out), the timezone from `timedatectl` / `/etc/localtime`. The same setup-core calls as Windows (`init`, `prepare-start`, `status`). **Both scripts run compose from the install folder**: compose reads `.env`'s `COMPOSE_FILE` relative to the folder it runs in, not to `--project-directory`. Verified in an Ubuntu 24.04 container with its own Docker Engine (Docker-in-Docker); ShellCheck clean.

### Run the CLI
```bash
python -m src.cli -d <devices.csv> -c <commands.txt> [-vf] [-v]
```
- `-vf` / `--verify`: after the push, read each device's config and check every command; `-v` / `--verbose`: print logs to the console (always written to `logs/`)
- Missing paths are prompted for (asked again until the file exists); a prompted run also asks verify and confirms ("About to push N commands to M devices") before the push — full-flag runs never ask. The verify choice is always printed. Exit code: 0 all devices succeeded, 1 mixed, 2 nothing applied (including a stop before the push: missing file, no devices or commands left), 130 Ctrl+C. Every exit but Ctrl+C waits for Enter when run from a terminal, so a double-clicked window stays readable. `--version` prints the version.
- **Standalone `netrollout-cli.exe`** (no Python needed; same flags): `pyinstaller --clean --noconfirm packaging/netrollout-cli.spec` from the repo root in the dev venv → `dist/netrollout-cli.exe` (one file, ~15 MB, ~2 s startup; logs go to `logs/` next to it). The CLI must not import the web stack — `tests/unit/test_cli.py` guards it, and the spec excludes it. The exe is unsigned: Windows Defender / SmartScreen may flag it (code-signing is post-v1.0).

### Build the release files (stage 9.9b; stage 10's release job calls it)
```bash
python packaging/build_release.py --version <VERSION> [--linux | --windows] [--feed-base URL] [--notes FILE]
```
→ `dist/release-<v>/`: `netrollout-<v>-linux.zip` (the update contract in `src/setup/update.py`: under `netrollout/`, Unix entries with modes, LF), `NetRollout-Setup-<v>.exe` + `netrollout-cli-<v>.exe` (Windows only: the Manager's `build.ps1`, Inno Setup — a local ISCC or its container — and PyInstaller), `SHA256SUMS`, and with `--feed-base` a `release-feed.json` as GitHub's API describes the release (a mirror; or a test of the Manager's Update / `update --feed`). ### Build the app image
```bash
docker build -t netrollout .                              # the version is the VERSION file
docker build --build-arg VERSION=1.0.0 -t netrollout .    # a release: the label; fails unless it equals VERSION
```
`python:3.12-slim-bookworm`, non-root `netrollout` (uid 10001), `NETROLLOUT_DEPLOYMENT=docker`, `NETROLLOUT_HOME=/data`; health check on `/_netrollout/health`. Context = the `.dockerignore` whitelist (also `VERSION` and Grafana's setup + dashboards, run by the `grafana-setup` service from this image — no bind mounts). The footer (`templates/_footer.html`) shows the version and links the source of that version (AGPL §13).
- Postgres: the **official `postgres:17-bookworm`** image, no extension (9.9a: pg_cron and the custom image dropped — the clean-up runs in the app; bookworm kept, as another base could change collations under an existing database), `timezone`/`log_timezone` from `TZ` (compose `command`). First start only (empty volume): `deploy/initdb/10-netrollout.sh`, mounted from the install folder into `/docker-entrypoint-initdb.d`, creates the logins `netrollout` (the app: owns the `netrollout` DB and `public`, not a superuser) and `grafana_reader`; env `POSTGRES_PASSWORD`, `NETROLLOUT_DB_PASSWORD`, `GRAFANA_DB_PASSWORD`. Installs from before 9.9a keep a pg_cron extension and jobs in their database: inert (no library loaded), never touched. NetRollout needs any PostgreSQL 13+ (`gen_random_uuid()`), no extension, no special server setting. At every start `install()` gives `grafana_reader` SELECT on exactly `GRAFANA_TABLES` (`device_results`, `job_metadata`, `audit_log`) when the role exists.
- nginx image (`deploy/nginx/`, `docker build -t netrollout-nginx deploy/nginx`): `nginx:1.30-alpine`; one site template (`site.conf.template`) rendered from values — env `NETROLLOUT_HOSTNAME`, `NETROLLOUT_HTTPS_PORT`, `APP_UPSTREAM`, overridden by `shared/site.env` (the app, stage 8; values are validated, never nginx syntax). Other names redirect to the hostname (IPs and localhost are served); port 80 → `https://<host>:<port>`; `/rollout/stream/` unbuffered; `/metrics` 404; the app looked up per request (Docker DNS, 10 s). `netrollout-watcher.sh`: waits for the certificate at boot; every 3 s (`NETROLLOUT_WATCH_INTERVAL`) a change of `site.env` or the certificate is rendered + `nginx -t`-tested in staging, then swapped in and reloaded, else the last good site keeps serving; the outcome in `shared/status.json` (`applied`/`rejected` + nginx's message).
- **Grafana** (monitoring profile): served by nginx at `/grafana/` to **signed-in NetRollout admins only** — nginx's `auth_request` asks the app (`/_netrollout/grafana-auth`: 204 + `X-NetRollout-User`, 401 → sign-in, 403 → "admins only"), Grafana runs in proxy-auth mode trusting `X-WEBAUTH-USER` (always set by nginx from that answer; a browser's own is replaced, `Authorization` dropped); every Grafana user is an Editor, no login form. Grafana's own administrator (the one `grafana-setup` signs in as) is `netrollout-grafana-admin` (`GF_SECURITY_ADMIN_USER`) - a name NetRollout refuses for its accounts (`accounts/users.is_reserved`: Add user, Request access, a directory sign-in, the directory import; its own message, not "taken"), since Grafana trusts the username nginx hands it; `grafana-setup` renames an install's pre-rc1 administrator `admin` (NetRollout's factory account's name, which Grafana then signed in as its administrator) and, on every run, demotes any Grafana server admin and makes every other user an Editor. Admins only because free Grafana lets anyone signed in query every datasource through its API (operators: post-v1, a separate organization — workplan). `grafana-setup` (app image, `deploy/grafana/setup.py`) keeps the layout: `NetRollout` → `Operations`/`Jobs`/`Security` (the shipped dashboards, dashboard v2 files in `deploy/grafana/dashboards/<subfolder>/`, re-imported, **view-only**) and `Custom` (the admins': create/edit/nest; never touched — backups must include Grafana's volume). It re-applies every 5 min and stays running (`up --wait` counts an exited container as a failure). **The NetRollout database data source** (uid `cfjxoedixn7r4d`, which the dashboards use; name "NetRollout database") is kept by grafana-setup through Grafana's API, not provisioned (a provisioned one is read-only): from `config/runtime.env` (mounted read-only; `PG_*` / `DATABASE_URL`, a host's 127.0.0.1 = the bundled `postgres`, `NETROLLOUT_GRAFANA_SSLMODE` written by the move from the app's own `pg_stat_ssl`), else the bundled database; the file is looked at every 5 s, a change applied at once (a database move: verified, 5 s); login `grafana_reader` with `GRAFANA_DB_PASSWORD` (grafana-setup's env, no longer Grafana's). The provisioning file deletes the earlier versions' provisioned `postgresql` by name (`deleteDatasources`); until Grafana restarts after an update, grafana-setup reports "restart Grafana" instead of failing silently. In a schema of its own, `grafana_reader` gets `search_path` = that schema per database (the DBA's SQL / the administrator-login way). The admin sidebar's Grafana glyph shows when `NETROLLOUT_MONITORING` contains `monitoring` (compose passes `COMPOSE_PROFILES`).
- The app → nginx (`src/access/nginx.py`): `write_site()` writes `site.env` in `config/nginx/` (shared with nginx) — the System Settings hostname plus the **applied** HTTPS port (`NETROLLOUT_HTTPS_PORT` from compose, not the setting, which waits for `netrollout apply`) — atomically and only when it changes; `read_status()` / `wait_for_status()` read the watcher's verdict (`None` = no nginx reports there). Every app start syncs it (`sync_at_start`, never blocks the start); the dev stack's nginx shares the repo's `config/nginx`, so dev follows too. **Saving the hostname** (System Settings → `app.access.save`: `Access`, `src/access/service.py`, the facade over the settings, the certs folder, nginx and the port request) is all or nothing: `SettingsStore.plan()` validates without writing; `Nginx.change_hostname()` renames the certificate by its kind (`CertificateStore.rename` → `Certificate.rename_to`: `SelfSigned` reissues it for the new name, keeping its IPs and the previous names for a 7-day transition — deadlines in `certs/.old-names.json`, dropped by `CertificateStore.drop_expired()` at start and hourly, `CertificateUpkeep`; `Organisation` is never reissued and refuses a name it doesn't cover), then writes `site.env` (any failure → `ProxyError`, files restored); the setting is saved; `Nginx.apply` awaits nginx's verdict for that hostname — rejected → setting, `site.env` and certificate put back. The page shows applied / not managed (own proxy) / no answer, or the reason under the field. The Access card always shows `Access.overview()` (`Nginx.overview`) — nginx's last verdict (applied / rejected + nginx's message, when) and the certificate in use checked by `certs.validate` against the saved hostname (names, expiry, self-signed or not, problems/warnings, old names in transition); it comes with the page, every save, and (in Docker) the Test button, which can't probe the published port from inside. **Server Management → TLS Certificate** (`admin_servers`, the same status via `templates/_access_status.html`): upload an organisation's certificate + key (`Access.upload_certificate` → `CertificateStore.install`: `certs.validate` against the saved hostname first — any problem refuses it; key written first; the self-signed marker and old names removed) or **Generate self-signed** (`Access.generate_selfsigned` → `CertificateStore.generate_selfsigned`: the saved hostname, else the current certificate's name, keeping its IPs); both wait for nginx's verdict (`Nginx.apply`) and put the previous files back on a rejection; audited (`server.certificate_uploaded` / `_generated`, never the key).
- **`config/nginx/site.env`** (`src/access/site_env.py`, the only code writing it; keys updated together under a lock, the file replaced atomically): the hostname and the port in use (nginx reads only these two), the port request, its id and time, and its confirmation (the port helper's); the installer writes the first hostname there and the app seeds System Settings from it at the first start (`nginx.seed_hostname_from_site`). Compose passes nginx no hostname or port and the app no seeds; the app gets the published port and `NETROLLOUT_SERVER_IPS` (in every generated self-signed certificate).
- The HTTPS port → the **port helper** (app side `src/access/port.py`; decisions `src/setup/port.py`; Docker by the scripts' `apply`; contract in `src/setup/port.py` and `src/access/port.py`, overview in `docs/architecture.md` §9): the setting is the **desired** port; saving (or Reset) writes the request into `site.env` (port + a new request id) before the setting, all or nothing. The helper opens the new port next to the old one — a trial file `config/port-trial.yaml` (`P:443` for nginx) listed in `.env`'s `COMPOSE_FILE` for the trial, nginx recreated (`up -d --no-deps --wait nginx`; nginx's config never changes for a port: it always listens on 443 inside) → `apply-status.json`: `trying`; the page served on the new port confirms (`/admin/settings/port/confirm` → `site.env`'s `PORT_CONFIRMED`; checked against the Host header's port and the deadline) → kept (`.env` `HTTPS_PORT`, `site.env`'s port in use, the trial removed); not confirmed within 120 s → rolled back. The 120 s are timed by the script's stopwatch (Docker Desktop's VM clock lagged Windows' by minutes once); a second `apply` waits for the lock, the running one looks again after a keep. **Automatic**: Windows — `NetRollout Manager.exe --helper` (headless, own single-instance lock; Startup entry, Setup's end, `netrollout start`; watches `site.env`, starts `apply` when a request is pending - one left pending (Docker stopped) is retried after 15 s, 60, 120, 240, then every 5 min; `logs\port-helper.log`, an apply's output only when it differs from the last; never a dialog); Linux — systemd `netrollout-port-<project>.path` (`PathModified=` site.env) → `.service` (`"<folder>/bin/netrollout.sh" apply --yes`, `%` written `%%`), written at every start, removed by uninstall; no systemd → by hand. Where a helper runs, `port-ready` writes a first status so the page waits for it instead of saying "run netrollout apply". Everything that shows or redirects to an address uses `serving_port()` (the helper's status, else `NETROLLOUT_HTTPS_PORT`). Page states: manual (no helper: `netrollout apply`) / waiting (bounded, `WAIT_SECONDS`) / trying / confirming / rolled back + Try again; its polls are background requests.
- TLS certificates (`src/access/certs.py`, inside the image so the host needs no OpenSSL): `python -m src.access.certs selfsigned --host <name> [--ip <addr>]...` writes `fullchain.pem` + `privkey.pem` + a `.selfsigned` marker (ECDSA P-256, 825 days, the IPs as SANs) to the certs folder; `validate --cert --key [--host]` checks key match, encrypted key, dates, SAN/wildcard coverage, chain order.

### Run tests
```bash
pytest                    # all
pytest tests/unit         # hermetic, no services
python -m mypy            # the type gate (pyproject.toml): every function in src/, the release build and Grafana's setup typed
```
End-to-end checks (`tests/e2e/`; skipped unless `NETROLLOUT_E2E=1`, so a plain `pytest` needs no Docker): a scratch install from the release's files and the images by tag, compose project `nre2e` on ports 18443 / 18080 — never the dev stack or an install:
```bash
docker build -t itamarweinstein/netrollout:e2e-local . && docker build -t itamarweinstein/netrollout-nginx:e2e-local deploy/nginx
NETROLLOUT_E2E=1 python -m pytest tests/e2e     # ~1.5 min with the images built; tears down with its volumes
```
`NETROLLOUT_E2E_TAG` (default `e2e-local`), `NETROLLOUT_E2E_BUILD=1` (build both first; else a missing image fails the run), `NETROLLOUT_E2E_DIR` (the scratch folder, new, empty or an earlier run's - anything else is refused; default a temp one), `NETROLLOUT_E2E_KEEP=1` (leave containers + folder; then `docker compose -p nre2e down -v` from it). CI: the informative job "End-to-end (informative)" (never fails the run, not required).
Code is documented in reST (`:param:` / `:returns:` / `:raises:`) on non-trivial functions; comments only where the logic needs explaining. Tests aren't typed — each says what it checks and expects.
Integration tests use a real Postgres (`rollout_test` DB, created on the dev stack's Postgres as its superuser — password from `.env`; `TEST_PG_ADMIN_URL` overrides) and Redis (db 15 of the server in `config/runtime.env`; `TEST_REDIS_URL` names another server or db — two runs side by side each need their own db and `TEST_PG_DBNAME` (a run also uses the db two below its own — `test_redis_switch` — so keep them apart, e.g. /15 and /11); the app's own db is refused, the tests flush theirs) and are skipped with a reason when a service is unhealthy — if ~150 skip right after `docker` starts, Postgres wasn't ready; rerun. LDAP tests start and remove an ephemeral OpenLDAP container. Known bugs are recorded as strict xfails.

### Migrations
```bash
cd src/db && alembic revision --autogenerate -m "..."   # new migration
```
The app applies migrations itself at startup; the alembic CLI resolves `DATABASE_URL`, else `PG_*`. History starts at the `v1_0_0_baseline` revision (the development migrations were squashed); from v1.0.0 on, released migrations are never edited or squashed — every schema change is a new revision.

### Configuration
- Folders (`src/runtime.py`, resolved per call): `NETROLLOUT_HOME` (image: `/data`), else the exe's folder when frozen, else the repo root → `logs/`, `config/`, `certs/`.
- Connection settings: `DATABASE_URL` or `PG_HOST/PG_PORT/PG_NAME/PG_USER/PG_PASSWORD/PG_SCHEMA` (a schema is a plain lowercase name, `^[a-z_][a-z0-9_]{0,62}$` — refused otherwise, at load and in the move form); `REDIS_URL` or `REDIS_HOST/REDIS_PORT/REDIS_DB/REDIS_PASSWORD`. A switch writes every key of that service, blank when unused (URL, password, schema), so nothing inherited can override it. Dev keeps its settings in `config/runtime.env`.
- Other env: `SECRET_KEY`, `PORT` (internal app port, set at install), `NETROLLOUT_THREADS` (Waitress worker threads, default 32, 4–256: an open live rollout log holds one for the whole rollout, and with as many open logs as threads every other request waits — measured 7 s with Waitress's default of 4).
- **System Settings** (admin panel → System; `src/db/settings.py`): retention periods, concurrent rollout jobs, devices per job, reachability cache, canonical hostname + HTTPS port. Cross-setting rules are declarative and enforced on the server and in the page.
- Deployment (`src/runtime.py`): `NETROLLOUT_DEPLOYMENT=docker` (set by the image) → `SECRET_KEY` and the encryption key are required (never defaulted or generated), Restart exits and the restart policy brings it back, no startup proxy probe (one log line with the expected URL instead). Dev: a missing `SECRET_KEY` gets a random per-run key.
- Startup in dev (`src/webapp/startup.py`): verifies nginx forwards to this instance (per-run token at `/_netrollout/instance`) and prints the address to use — the System Settings hostname + serving port, else `https://localhost`; opens it in the browser on desktop launches (`NETROLLOUT_OPEN_BROWSER=0` to disable).

### Backups (`src/backup/`, stage 9.5)
`python -m src.backup create [--kind manual|scheduled|before-restore|before-update] | check <zip> | restore <zip> [--grafana-dir] [--https-port] [--key-out]` → `backups/netrollout-<version>-<YYYYMMDD-HHMMSS>-<kind>.zip`: `manifest.json` (version, migration level, row counts), `db/<table>.csv` (NetRollout's tables, one read-only REPEATABLE READ snapshot, `COPY … CSV HEADER`), `grafana.db` (SQLite online backup of the read-only mounted volume), `certs/`, the rollout logs, `encryption.key` — the zip is as secret as `.env` (owner-only). ### Object model
The design rules (the 2026-10 redesign): a class only for a real thing with state and behaviour — a rule without state stays a function; an ABC when we own the whole family and the base shares code (`Finish`, `Certificate`, `Setting`, `ServiceConnection` — a template method —, `PeriodicTask`), a Protocol when the implementer is foreign or a test fake (`ConfigSession` = Netmiko, `KeyValueStore` = redis-py, `Echo`, `Notifier`, `SessionSerializer`), a `Callable` for a one-call contract (`hold`, `retention_days`, the per-call `postgres` / Redis lookups); an enum when a closed set of values is spelled twice or crosses a boundary (Redis, a file, the database, JSON, a script) — its values never change; `isinstance` only to validate external data, never to choose behaviour; one file = one concern; domain services (`InventoryView`, `JobResults`, `Accounts`, `SecurityProfiles`, built as `Service(session, viewer)`) work in the caller's session and **raise** (`RuleRefused`, `AccountError`, `SettingsError`, `ProxyError`; the routes' own helpers `load_owned` → `NotFound`, `Refused`) — the route catches **outside** its session block, so a refused change rolls back instead of committing half. Details per package: `docs/architecture.md` §11.

Retention (defaults; System Settings): job record (results + metadata) 30 days, config snapshots 7 days, audit log 90 days — the **nightly clean-up runs in the app** (`src/db/retention.py`: daily at 03:00 server time on whatever database it's connected to, a missed time caught up once, a failure retried after an hour; `retention.run_retention` runs `RETENTION_STATEMENTS`, which read the setting's row at run time; the last outcome in `config/retention-status.json`, shown on System Settings → Retention); log files 60 days (app-side, daily: `LogPruner`).

### Rollout job state
`src/jobs.py` (`JobStore`) owns the Redis job keys (`job:{id}:meta`, `user_jobs:{uid}`, the queue, the pending/active counters): the orchestrator writes through it, the pages and the Prometheus collector read through it — no other code spells a key. Every start clears leftover job state, live log histories included (`jobs.clear_stale_jobs`: jobs live only in their process, so anything there came from a crash). A `submit()` failing partway withdraws the job (nothing left in memory or Redis); a status is written only to a job's existing hash (`set_status`, a Lua HSET-if-exists), so a cancel racing the job's end leaves no phantom row. Each queued job is claimed once under the lock (`RolloutJob.claim()`: the dispatcher to start it, a cancel or the drain to record it); **cancelling a queued job ends it at once** (recorded as cancelled, "Cancelled before it started"), a running one is asked to stop. The pages say a queued job is "Queued — waiting for a free slot" (Active Jobs, the dashboard's card). A finished job (`RolloutOrchestrator._finalize`): results to Postgres (`ResultRecorder`, retried; still failing → `logs/unsaved-results-<job>.json` + an ACTION NEEDED console line), then the Redis cleanup and the live log's end — each step runs even if another failed.

### Webapp real-time logging
Server-Sent Events at `/rollout/stream/<job_id>` (`RolloutJob.follow_log` → `LiveLog.follow`): subscribed to `job:{id}:logs` first (confirmed), then the history (`job:{id}:history`; key names from `rollout/log.live_log_keys`), then live messages — published as `<n>	<line>` (n = the history's length after the push), so one already in the history is skipped; `__done__` ends it. A queued job's stream starts with "Queued — waiting for a free slot" (the stream's only, not in the job's log) and waits; it ends when the job has run (`is_over`) or the orchestrator no longer has it. A job not here (just finished) gets only the `done` event (owner/admin, by `JobMetadata`), else 403 / 404. Each message is `data:` per line (multi-line messages whole); the heartbeat every 0.5 s is a comment (`: hb`). The live log is best-effort: the log file is written first, a Redis error never fails the rollout. `X-Accel-Buffering: no` disables nginx buffering.

### Supported platforms (Netmiko device types)
The list is `SUPPORTED_PLATFORMS` (`src/rollout/inputs.py`, derived from `PLATFORMS`; the pure input checks are module functions there, `Validator` only checks the CLI/import files); how each one finishes a push and prints its config is the `PLATFORMS` dict in `src/rollout/platforms.py` (platform knowledge only, no I/O of its own: a `Platform` row names its `Finish` — `SaveConfig` / `Commit` / `RunCommand` / `NoFinish`, acting on the session it is handed —, also `rejection()` and `verify_commands()`); the SSH conversation is `NetmikoSession` (`src/rollout/session.py`: the push, the finish, the config fetch; it writes the rollout's `RunReport`); `src/rollout/engine.py` runs the devices in parallel, and its status rules are `classify()` — adding a vendor is one row there plus a fixture in `tests/unit/rollout/test_platforms.py`. Cases only a person can resolve are logged as `ACTION NEEDED — <ip:port>: …` and counted in the rollout summary. Job logs are safe to share: every log line (file, Download Log, live stream, console) and every stored ACTION NEEDED text passes `rollout/log.redact` - the value after `password` / `secret` / `community` / `psksecret` / … becomes `<redacted>` (the commands as typed and config snapshots aren't redacted). Verify (`verify_commands`) places each typed command in its config section and checks presence / absence (`no`/`undo`/`delete`/`unset`); all 12 platforms are covered.

### Device CSV format (shared by CLI and web import)
Required: `ip` (IPv4 or IPv6 — everywhere: the forms, the CSV import, the CLI; an endpoint is written `ip:port`, IPv6 as `[addr]:port`, by `rollout/engine.endpoint`, also a template filter), `device_type`, `port`. Optional: `label`; credentials `username`, `password`, `secret`; attribute columns named after a property (by name or label).
- **CLI**: credentials required; attribute columns unused; unreachable devices are dropped before the push.
- **Web import**: attribute columns saved as the device's values — a system property's in its `var_maps`, a custom property's as the importer's own (`device_attributes`); credentials become security profiles (checkbox, default on — exact match reuses a profile, otherwise a new uniquely labelled one); unknown columns reported; no reachability check.

## Working style
- The developer writes the code; Claude reviews, advises, and discusses design
- Exception, granted per feature: the developer may approve Claude writing backend code for a specific feature — plan first, stick to the approved plan, and verify on a scratch DB (never the live one) before touching real data
- Always read actual source before suggesting changes
- **Imports** (the style of `jobs.py`, `rollout/engine.py`, `cli.py`): all at the top, after the docstring — `from __future__` first, then three groups separated by a blank line: standard library, third-party, the project (`src` / `tests`); in each, plain `import x` before `from x import …`, sorted by module; no comment headers (`# flask`, `# local modules`). No import inside a function, except `src/db/alembic/env.py`'s (after the project root is put on `sys.path`, on purpose). The rollout engine (`src/rollout/`) imports the DB models and Redis for type checking only: the CLI `.exe` must not load the web stack. No cycles: every module imports on its own.
- Frame architecture feedback in terms of encapsulation, minimal API, abstraction, information hiding
- Developer has real networking domain knowledge (3+ years, Netmiko/NAPALM fluency) — no need to explain networking basics
- Distinguish critical issues from design improvements from minor polish when reviewing
- For frontend work, Claude writes the templates/HTML directly (exception to the "developer writes" rule)
- **Changing an existing test needs a proper reason, stated in the commit** — a behavior change the developer approved, a wrong fixture/expectation proven against the source or the vendor's documentation, or a rename. A failing test is a finding first: fix the code, or report it. Never edit an expectation to match what the code now does (retrofitting) without the developer's approval, never loosen an assertion (exact → "somewhere", value → truthy) to make it pass, and never add `skip`/`xfail` to get green. A new test must fail without the change it covers.
