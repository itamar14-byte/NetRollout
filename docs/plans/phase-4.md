# Phase 4 — packaging NetRollout v1.0.0

## Context
NetRollout is feature-complete on `master` (System Settings merged 2026-09-30). Phase 4 turns it into a free community product (GNU AGPL v3) that a team installs with minimal friction: download a release zip, run the installer, answer a few questions, get a running HTTPS NetRollout. This plan records the vision agreed in the planning session and the staged implementation.

_Approved 2026-09-30. Branch `phase-4-packaging`. Status: stages 1–7 done (2026-10-04) — the dev DB is stamped `v1_0_0_baseline`, so `master` can't start against it until the Phase 4 fast-forward; dev settings moved to `config/runtime.env`; next: stage 8._

## Vision
- **Three uses:** (1) engineer's PC, (2) **team server — main case**: a Windows 10/11 VM running Docker Desktop, reached remotely over HTTPS, (3) **headless CLI** as a standalone `netrollout-cli.exe` (no Docker/Python).
- **Delivery:** public GitHub release zip (v1.0.0, semver) + images on Docker Hub (`itamarweinstein/netrollout`, `-postgres`, `-nginx`). The zip is a compose project: `compose.yaml`, service configs, installer, management + update scripts.
- **Stack:** app, Postgres (pg_cron), Redis, nginx; optional monitoring profile (Grafana, Prometheus, Loki, promtail). **Only nginx publishes ports** (443, and 80→443 if free). Grafana through nginx at `/grafana`. `restart: unless-stopped` everywhere.

## Decisions (planning session 2026-09-30)
1. Windows (main) and Linux supported; the installer detects the OS. Windows = **Docker Desktop on Windows 10/11** (Windows 11 recommended; Win10 is past end of support). Windows Server is detected and refused (unsupported by Docker Desktop). Linux = Docker Engine + compose plugin.
2. VM prerequisites documented + checked: **nested virtualization**, vTPM + Secure Boot for Win11, ~4 vCPU / 8 GB RAM (16 GB with monitoring). **Auto-logon for a service account** so NetRollout comes back after reboots (Docker Desktop starts at sign-in).
3. **Licensing notice** before install — Docker Desktop terms (free only for small orgs; compliance is the org's), NetRollout AGPL v3, Windows client-VM licensing — the user must type **yes**; acceptance recorded in the install folder. Docker Desktop is **never bundled** — the installer links to Docker's official download.
4. **Installer questions** (`[default]`, Enter accepts): hostname [computer name], HTTPS port [443], monitoring [Y], organisation certificate path [none → self-signed], concurrent rollout jobs [4], timezone [UTC]. Generated silently: Postgres/Redis/Grafana passwords, `SECRET_KEY`, the Fernet encryption key. *(Revised from the session: the "internal app port" question is dropped — the app port is internal to the compose network and never published, so it can't clash; timezone added — containers run in UTC and the app stores naive local times.)*
5. **Data:** Postgres/Redis/Grafana/Loki in named volumes; `logs/`, `config/`, `certs/`, `backups/` as visible folders in the install folder.
6. **Management script** `netrollout` (.bat/.ps1/.sh): start, stop, status, open, logs, backup, restore, apply. Separate **update** script (auto-backup → new version → pull → up; migrations at app start). In-app "check for updates" is post-v1.0.
7. **Admin Restart** in a container: the app exits cleanly and the restart policy brings it back; refused while rollouts run (unless forced).
8. **Factory admin** stays `admin`/`admin` with a forced **change-password at first login** (blocking page).
9. **Certificates:** self-signed by default, organisation cert via the installer, and **upload in Server Management** (validated, applied live by nginx's watcher).
10. **Part C:** System Settings hostname applies live (nginx config rendered by the app, validated + reloaded by a watcher; other names redirect to the canonical hostname; a self-signed cert is regenerated for the new name). HTTPS port changes need `netrollout apply` (no host networking on Windows).
11. **CLI** as a PyInstaller `.exe`, built in CI.
12. **Release pipeline:** GitHub Actions on a `vX.Y.Z` tag.
13. **CDN assets stay** for v1.0 (bundling + offline image transfer post-v1.0).
14. **Squash the migration history** into one v1.0.0 baseline before release; dev DB `alembic stamp`ed.
15. **Platform profiles before v1.0** (found 2026-09-30): the push never commits on Junos / PAN-OS / IOS-XR and reports five platforms as failed (`save_config()` not implemented there), and verify is broken on 7 of 12 platforms — IOS-XE mapped to a non-existent NAPALM driver (`iosxe`), Juniper returned in curly-brace format so typed `set` commands never match, FortiOS/PAN-OS/Aruba CX/ProCurve NAPALM drivers not installed, and the verify connection ignores the device port. Fix: fetch the config via **Netmiko** (already the push library; all 12 platforms; honours the port) **in each vendor's typed syntax**; NAPALM dropped as a dependency. Deep Diff + `hier_config` + `netutils` stay in Phase 5b; an optional local-AI "explain this failure" is a post-v1.0 idea.
16. **Community release** _(decided 2026-10-04)_: v1.0.0 ships with platforms the developer couldn't test on real devices, in exchange for bug reports and feedback (AGPL: reporters can see — and often fix — the cause). To make that trade work: say which platforms are tested (README support table, promoted as reports confirm them); make a good report easy (issue templates); make job logs safe to post publicly (secrets redacted); safe defaults for first-time users (Verify on, "try it on a lab device first"); semantic versions (fixes are 1.0.x, `update` picks them up).

## Implementation — stages (each on its own branch, testable and committable)

**1. Hygiene.** `requirements.txt` fixed (add Flask-WTF; drop mypy, pytest, pip, utils, ipaddress, numpy, dotenv) + `requirements-dev.txt` + a pinned lock file; Python 3.12. `.gitattributes` (LF for .sh/nginx files, CRLF for .bat/.ps1). `.dockerignore` as a whitelist (`src/`, `templates/`, lock file only — keeps `docs/credentials`, `config.env`, `logs/` out). `LICENSE` (AGPL-3.0). **Migration squash** (decision 14): baseline from models, `alembic check` on a fresh scratch DB, stamp the dev DB.

**2. Paths + config precedence.** New `src/paths.py` decides folders: `NETROLLOUT_HOME` (image: `/data`), else the exe folder when frozen, else the repo root (dev unchanged); `logs_dir()`, `config_dir()`, `certs_dir()`. Callers: `logging_utils.LOGS_DIR`, `jobs.py` log lookups, `startup.DEFAULT_NGINX_CONF`, `backend._CONFIG_ENV`. Two config files: compose `.env` (installer-owned → container env) and `config/runtime.env` (app-owned, written only by Server Management, loaded with override) — precedence runtime.env > container env > defaults. Remove the unused `pending_db_init.flag` and `*_EXTERNAL` writes; fix `connection_modes()` to treat the compose hosts as bundled.

**3. Container runtime.** _(Revised 2026-10-01 with the developer: the startup proxy probe is dev-only; stop/Restart drain running rollouts.)_ Explicit `NETROLLOUT_DEPLOYMENT=docker`. Fail fast in a container on a missing `SECRET_KEY` or encryption key (never generate a key inside a container); in dev a missing `SECRET_KEY` gets a random per-run key + a warning (no `"dev"` fallback). **Drain** (one routine for SIGTERM and Restart): new rollouts are refused with a clear message and a banner; running rollouts finish; queued ones are marked cancelled ("server restarted before it started") instead of silently vanishing (job definitions live only in memory); bounded by a deadline (default 10 min, below compose's `stop_grace_period`) after which running jobs are cancelled with a record. Restart route (`admin_servers.py`): with rollouts running it answers 409 and the page offers "restart when rollouts finish" (drain) or "restart now" (cancel), in dev and container alike; container → drain + `os._exit(0)`, the restart policy (`unless-stopped`) brings it back. Startup message: in a container no proxy probing and no browser — one log line with the expected URL (System Settings hostname + HTTPS port); the host-side check is the installer and `netrollout status` calling `/_netrollout/health` (stage 9); the token probe stays for dev. `/metrics` → 404 in nginx, scraped by Prometheus at `app:8080`. Flask-Session reads the live Redis client (a Server Management Redis switch keeps logins working). New `/_netrollout/health`: Postgres/Redis status, running/queued rollouts, version; 200 when both services are up, else 503.

**4. Passwords: forced change, self-service change, admin reset.** _(Extended 2026-10-01 with the developer: until now no user could change a password.)_ Migration (the first on top of the baseline): `users.must_change_password` (true for `admin` while its hash is still "admin"); seeding sets it. One password rule everywhere (registration, change, generated): at least 8 characters with at least 2 of letters / digits / special characters, ASCII, not containing the username (so never "admin"); a change must differ from the current one. One `before_request` gate while the flag is set (allowlist: the change-password route, logout, static, instance/health): pages redirect to the change page, JSON/XHR gets 403. `/account/password` + `templates/change_password.html` (current + new + confirm) serves both the forced change and a voluntary one (a link on the Account page); rate-limited like login; audit `auth.password_change`; flag cleared; session rotated; the user's other sessions signed out. Admin "Reset password" for another local user: a random temporary password shown once to the admin, the stored password replaced, the flag set, the user signed out everywhere (every session, not only the latest), audit `user.reset_password` (never the password); not for LDAP users, the admin's own account or the factory `admin`. Local accounts only.

**4b. Platforms: push finalisation + verify (decision 15).** _(Converged 2026-10-02 with the developer after a hier_config spike; kept small — no new module, no new dependency.)_ Found 2026-09-30 (netmiko 4.6.0): the push (`RolloutEngine._push_device`, `src/core.py`) always ends with `save_config()`, which Netmiko doesn't implement for Junos, PAN-OS, IOS-XR, FortiOS and Check Point → the device is reported failed, and **Junos / PAN-OS / IOS-XR changes are never committed** (leaving config mode discards them). Verify (NAPALM `get_config`) is broken on 7 of 12 platforms and ignores the device port; a rejected command doesn't fail the device.
- **One `PLATFORMS` dict in `core.py`** (12 rows, replaces `netmiko_to_napalm`): how to finish (`save_config()` for Cisco IOS/IOS-XE/NX-OS, Arista, Aruba CX, HP ProCurve/Comware; **`commit()` before leaving config mode** for Junos, PAN-OS, IOS-XR, a commit error is a failure with the device's message; `save config` for Check Point Gaia; nothing for FortiOS), the command(s) printing the config in the syntax engineers type (Junos `show configuration | display set`; PAN-OS `set cli config-output-format set` + `show config running`; Gaia `show configuration`; FortiOS `show`; Comware `display current-configuration`; the rest `show running-config`), and whether that config is flat (`set …` lines). Adding a vendor = one row + a fixture test.
- **Fetch over Netmiko** (the push library: all 12 platforms, the device's port and credentials); `napalm` removed from the requirements.
- **Verify** = a plain indentation parser (the flat configs are a one-level tree) + **placing each typed command in its section** from the post-push config's own structure (a typed line that is a section there opens it; `exit`/`end`/`next`/`quit`/`return` close; a global command typed inside a section leaves it; a command that didn't apply stays in the section) + a present/absent rule: a command must exist at its place; `no X` passes when `X` is gone; `delete X` when no `set X…` line remains; operational commands (`commit`, `write`, `copy`, `clear`, `do`, `show`, `save`) are **not verifiable**. Per-command verdicts in the log; status (success/partial/failed) counted over verifiable commands only.
- **Rejected commands** (one combined list of vendor error strings) are reported with the device's message; the remaining commands are still sent; the device is partial (some rejected) or failed (all rejected) even without Verify.
- **Verify Diff** shows the server's verdicts (the route runs the same matcher on the stored config) — no second matcher in the browser.
- Spike result (kept in mind for 5b): hier_config 3.7 covers the indented platforms, but its `future()` (experimental) got negations wrong and its parser added nothing over the plain one here (44/44 identical verdicts) — it stays in Phase 5b for the remediation between before/after configs (`config_to_get_to`).
- Known remaining limits (documented, solved in 5b): typed abbreviations, values the device rewrites (hashed secrets, reformatting, hidden defaults), "already present before the rollout", multi-line banners, Junos `up` taken as leaving the whole last `edit`. Update the Verify tooltip on New Rollout. Tests: per-platform fixtures (recorded config output + commands → expected verdicts) incl. `delete`, `no …`, FortiOS nested blocks; push finish per platform with a mocked Netmiko; a port-forwarded device fetch uses its port. Real-device check: the EVE-NG round (release gate).
- Also in this stage (developer's request): `src/paths.py`, `src/deployment.py` and `src/version.py` folded into one `src/runtime.py`.

**Port helper** _(decided 2026-10-04; files merged in stage 9.1 — the request and confirmation are keys in `config/nginx/site.env`, see `docs/plans/stage-9.md`)_: a host-side service (Linux: a systemd `.path` unit watching `config/nginx/site.env`; the installer installs it — Windows/Docker Desktop needs its own trigger, e.g. a scheduled task) that applies a new HTTPS port with ~2–3 s of nginx downtime and never gives the app Docker access. **Contract** (files in `config/`; the app side is `src/webapp/port_apply.py`):
- `site.env` request keys — app writes (atomic, `src/site_env.py`): `NETROLLOUT_PORT_REQUEST=<port>`, `NETROLLOUT_PORT_REQUEST_ID=<hex>`, `NETROLLOUT_PORT_REQUESTED_AT=<epoch>`; a new id per request (also "Try again"). The helper handles each id **once** — a rolled-back id is never retried on its own.
- `apply-status.json` — helper writes (atomic), also at its start: `{"id", "state", "port", "trying", "deadline", "message", "time"}`; `state` ∈ `trying` (both ports published, `trying` = the new one, `deadline` = epoch seconds) / `applied` (`port` = the serving port) / `rolled_back` / `failed` (`message` = why: port in use, not confirmed in time, compose error). Absent = no helper: the page says "run `netrollout apply`". `netrollout apply` runs the same code once.
- `NETROLLOUT_PORT_CONFIRMED` (in `site.env`) — app writes the id when an admin's browser reached NetRollout **through the new port** (the page served there posts it; the Host header's port is checked — it only proves something to that admin, which is the point). Seen before `deadline` → the helper drops the old port and writes `applied`; else it removes the new one and writes `rolled_back`.
- **Server IPs for self-signed certificates** _(found in 8.5)_: "Generate self-signed" keeps the IPs the *current* certificate covers — after an organisation's certificate without IP SANs, the installer's server IPs are lost. The installer records them (`NETROLLOUT_SERVER_IPS` in `.env`, stage 9.1) and `generate_selfsigned` adds them (done in 9.1).
- Trial: the helper re-validates the port, checks it is free on the host, recreates nginx with **both** mappings (a generated compose override adding `<new>:443`), waits for health, writes `trying` (deadline ≥ 120 s — time to click through a certificate warning); on confirm it writes `.env` `HTTPS_PORT=<new>` (so a later `up` keeps it), recreates nginx with the new mapping only and removes the override. Any failure → the previous mapping is restored. Rollouts are untouched (only nginx restarts); sessions survive (cookies ignore the port). The app container keeps its old `NETROLLOUT_HTTPS_PORT` until recreated, hence the serving port comes from `apply-status.json`.

## Verification
- Every stage: the full pytest suite + new unit/integration tests; nothing starts against the live dev DB (scratch DB + Redis db 15 + spare port harnesses only).
- Images/compose: `docker compose --profile monitoring up -d --wait` on the developer's Windows PC — instance endpoint through nginx, `/metrics` 404, Grafana `/grafana/api/health`, dashboards reading Postgres/Prometheus/Loki, Loki timestamps correct, pg_cron jobs in `cron.job`, Restart button returns without a lasting 502.
- **EVE-NG platform round (stage 4b; one rollout per platform with a deliberate typo, a removal and Verify on, through the web app and the CLI `.exe`)** — priority: PAN-OS, FortiOS, Junos, IOS-XR (new commit/finish paths, least certain formats), then Comware and Check Point Gaia, then Cisco/Arista/Aruba/ProCurve as a sanity check. Open questions the documentation didn't settle: does PAN-OS operational `show config running` (set format) prefix vsys objects with `vsys vsys1`; Junos `configure private` refused while shared edits are pending (the failure must be clear, not a hang); FortiOS with VDOMs (prompts, `config global`, `cfg-save`); Gaia `show configuration` shows the running (not only saved) state; each vendor's rejection messages — and no false ones from the broad markers (`error:`, `% error`, `commit failed`) or from coded *informational* Gaia lines; FortiOS `execute cfg save` in revert mode may ask for confirmation; an Aruba CX rollout with interface sub-contexts; a Gaia account whose shell is expert (the switch to clish); a PAN-OS failed commit (revert config / load config fallback); an IOS hostname change (saved from a new session) (commands are now sent without Netmiko re-entering config mode). A difference is usually one `PLATFORMS` row or one string + its fixture in `tests/unit/test_platforms.py`.
- Stop / Restart with a real rollout (stage 3 proved SIGTERM → drain → exit 0 only with the app idle, and the drain with fakes): `netrollout stop` and the Restart button during a running lab rollout — banner shown, the rollout completes and is recorded, a queued one shows as cancelled in Results, exit 0; Restart brings the container back (`unless-stopped`).
- Part C: hostname change applies live and old names redirect; organisation cert upload applies without restart; a bad cert is rejected while service continues; HTTPS port + `apply`.
