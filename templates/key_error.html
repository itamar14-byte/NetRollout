The encryption key this server uses doesn't match the key that encrypted {{ what }}. This usually means the database came from another install, or the key was replaced. Nothing was changed.

This server reads its key from {{ key_source }}.

Fix it: restore the original key

  1. Find the key that was in use when this data was saved: the {{ env_var }} value in your previous deployment config (config.env, docker-compose file or service definition), or the encryption.key file from the previous host's ~/.netrollout/ folder or a backup.
  2. Put it where this server reads its key: set {{ env_var }}=<original key> (the variable takes precedence), or replace the contents of {{ key_file }}.
  3. Restart NetRollout: the Restart button in the admin panel, or restart the process / container. Startup checks the key against the stored data and refuses to start, with the reason in the server log, if it's still wrong.

If the original key is lost

Those secrets can't be recovered. Replace them:

  • Security profiles: Security Profiles → edit each profile → type the password (and enable secret) again → Save.
  • LDAP: Admin → Server Management → LDAP → enter the bind password again → Save.
  • Two-factor sign-in: clear the affected users' 2FA so they enroll again at their next sign-in. Run in the NetRollout database: 
    UPDATE users SET otp_secret = NULL WHERE username = '<user>';
Don't generate a new key. A new key can't read the existing data, and anything saved afterwards would be encrypted with yet another key.
